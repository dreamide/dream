## ARC17-01: Chat turn outcome

Status: implemented

Problem: what a Chat's last turn came to is kept in three places, the
activity store's entries, the store's `completedChatIds` (the unread mark) and
the chat runtime's `errorByChatId`. About eight places write them:
`setChatStreaming` starts and interrupts activity as a side effect inside its
zustand updater; `handleChatError`, `handleChatFinish`, `observeSessionMessages`
and turn following's `onSettled` finish it or raise attention; four chat and
project actions clear the unread mark. Only this window's session writes any of
it, so a turn on the host this window is not following (another client's, or a
chat with no session here) never gets an activity entry, an unread mark or a
notification, although Chat activity counts it as running.

Scope: one Chat turn outcome module owns a chat's turn status (running,
waiting on its user, finished, failed, interrupted), its unread mark, its error
and their persistence. It takes events from two sources: this window's session
(chat runtime and turn following) and the host catalog's `turn` and
`approval` events. Seeing a chat clears its unread mark through it.
`setChatStreaming` becomes a plain flag. Chat activity (running, waiting,
accepts a message) keeps its own three answers. Copying the Provider session
onto the chat row in `handleChatFinish` is out of scope.

Completion criteria:

- One module writes turn status, unread mark and error; no other module calls
  the activity store's writers or sets `completedChatIds`.
- A host turn this window does not follow starts, ends and marks its chat
  unread, and notifies, like a followed one; a turn followed here is not
  counted twice when both sources report it.
- No side effect inside a zustand `set` updater.
- Tests through the module's interface cover: a session turn finishing, a
  session turn failing, a host-only turn ending, attention from a host
  approval, and seeing a chat clearing its mark.

Implementation: `createChatTurnOutcomes` in
`src/components/ide/chat-turn-outcome.ts` is the module, and
`chatTurnOutcomes` is this window's one. Its state is a vanilla zustand
store (`turns`, `unread`, `errors`) that readers select with
`useChatTurnOutcomes`; `turns` persists under the old
`dream-agent-activity-v1` key, a saved running or waiting turn reading back
as interrupted. The activity store (`activity-store.ts`) is absorbed and
deleted, the store's `completedChatIds` and the chat runtime's
`useChatRuntimeStore`/`errorByChatId`/`setChatError` are gone. Its interface:
`started(chatId)`, `attention(chatId, detail | null)` and
`ended(chatId, how?, detail?)` for this window's session; `reportError` for
a banner message that is no turn's end (a refused submission, a lost
stream); `seen(chatIds)`; and `watch(store)`, which follows the IDE store's
`hostRunningChatIds` and `hostAwaitingApprovalChatIds` (where the catalog's
`turn` and `approval` events and catalog reads land), reads which chat is
shown when a turn ends, and forgets chats that leave the store (a deleted
chat only loses its mark). `IdeShell` starts the watch.
Inside, each running turn records which sources report it. It starts with
the first and ends with the last, taking the most telling ending either
gave: a failure, then the session's own end (finished, or interrupted by a
stop), then the host's plain end (finished), then a session that only
stopped following (`ended` without `how`, interrupted only if nothing else
says otherwise). So a followed turn is counted once, whichever source ends
first. A failure is on the banner at once; a later failure without a message
or a later cleanup does not replace it. A finished turn whose session
transcript still asks its user something ends waiting. A host change that
starts, asks and ends several turns reaches readers as one write.
Writers now: the chat runtime calls `started` when following begins,
`attention` from each messages update and at finish, `ended` from
`handleChatError` (failed, with the banner message), `handleChatFinish`
(failed, interrupted or finished) and turn following's `onSettled`
(finished if the host already ended the turn, otherwise only stopped
following), and `reportError` where it called `setChatError`.
`setActiveChatId` and `setActiveProjectId` call `seen` after their `set`.
`setChatStreaming` is a plain flag with no side effect; `deleteChat`,
`permanentlyDeleteChats` and `project-runtime-state.ts` no longer touch
marks. `activity-notifications.ts` watches `turns`; the project tabs,
projects panel and code workspace read `unread`; the chat panel reads and
sets `errors`. Chat activity (`chat-activity.ts`) is unchanged.

Behaviour: a turn on the host this window does not follow now starts, ends,
marks its chat unread and notifies like a followed one. A followed turn
whose stream this window lost is no longer marked interrupted when
following stops; it stays running until the host says it ended, as Chat
activity already counted it. Clicking the project tab of the project
already in front no longer clears marks of its other chats (it clears them
whenever that project is brought to front). A chat removed from the store
takes its saved turn status with it, which the activity store kept forever.
The unread mark stays this window's and is not persisted, as before.

Validation: `pnpm check` passed (scratch check, `biome check .`,
`tsc --noEmit`, vitest: 226 files, 1633 passed, 4 skipped).
`chat-turn-outcome.test.ts` (12 tests) drives the module through its
interface over a watched vanilla store: a session turn finishing marks only
the chat not shown unread; a session turn failing shows its error at once,
ignores the AI SDK's later finish and ends failed when the host ends; a
host turn this window does not follow starts, ends and marks its chat
unread; a followed turn both sources report is one running/finished pair
whichever ends first; a stopped turn is interrupted though the host says
only that it ended; a session that only stops following leaves the end to
the host; a host approval makes the chat wait and answering it resumes
running, ending as one change; a session question is the turn's detail and
a turn ending on one waits; seeing a chat, or its next turn, clears its
mark; a deleted chat loses its mark and a removed one its outcome; turns
already running when the watch starts count; turns persist with running
read back as interrupted. `chat-runtime.test.ts` reads the outcome's
`errors` and `turns` instead of the removed stores; the notification and
store tests lost their `completedChatIds` fixtures and pass otherwise
unchanged.

Remaining/deferred: copying the Provider session onto the chat row in
`handleChatFinish` stays out of scope. The host reports no ending of its
own, so a host-only turn that failed or was stopped elsewhere is recorded
as finished. The app was not run.

## ARC17-02: Chat submission

Status: implemented

Problem: there are two ways to send a message to a chat. The composer calls
`submitChatPrompt`; the stash, saved prompts and feedback write a one-slot
`pendingChatSubmitByChatId` that a store subscription in the chat runtime
takes and submits. The slot exists only so the store does not import the
runtime. The gate deciding whether a chat can take the message is written
three times (`queueChatSubmit`, `isEmptySubmission`, `submitChatPrompt`) and
the copies differ. `submitChatPrompt` answers true, false with the reason on
the error banner, or throws, and the chat panel reads the banner back.

Scope: one Chat submission module with one entry point every caller uses,
answering sent, refused with a reason, or failed with an error. It owns the
gate once, serializing the submission, and putting the draft back on failure.
The runtime registers itself with the store as the submitter, as it does for
the host resolver, so the pending-submit slot goes. Chat activity's "accepts a
message" keeps its meaning.

Completion criteria:

- `pendingChatSubmitByChatId`, `queueChatSubmit` and `takePendingChatSubmit`
  are gone, or any survivor is internal to the submission module.
- The composer, stash, saved prompts and feedback send through the one entry
  point and get the same refusals for the same chat state.
- The result is a value; no caller reads `errorByChatId` to learn why a send
  did not happen.
- Tests through the entry point cover each refusal reason, a successful send,
  and a failed send returning its text to the draft.

Implementation: `sendChatMessage(chatId, submission, { origin })` in
`src/components/ide/chat/chat-submission.ts` is the one entry point. The
submission is `{ text, references, files?, skills? }` (serialized text; the
composer passes the skills it recognised, anyone else's are recovered by the
composer draft serializer, fetching the skill catalog only when the text could
mention one). `origin` is `composer`, `stash`, `saved-prompt` or `feedback`;
only the composer's message is the chat's draft (emptied once sent, left as it
is otherwise); every other sender lets go of its message when it sends, so one
that is not sent is appended to the chat's draft. The answer is
`{ status: "sent" }`, `{ status: "refused", reason, message }` or
`{ status: "failed", error }`, and the same message goes on the banner through
the Chat turn outcome's `reportError` (except a busy refusal, below). The
gate, in order: `not-in-active-project` (chat missing or deleted, project not
open, or not the active project), `empty` (no text, references or files; no
banner), `busy` (a message to the chat is still being sent from this window),
`host-away`, `provider-unavailable`, `no-model`. It is decided before the
promise is returned, so a second call at once is refused. From the gate until
the host has the message the chat is in the store's new runtime map
`sendingChatIds` (written only through `setChatSending`, by this module), which
replaces `pendingChatSubmitByChatId` in Chat activity's "accepts a message",
in the runtime state dropped with a project, and in the chat activity tests. A
message that passes activates its chat, waits for its transcript, retains its
session while it is sent, and calls the runtime's `startChatTurn`, which is
`submitChatPrompt` without its gate, banner or per-chat promise chain: it
builds the message, submits it with the lost-receipt retry and follows the
turn. The store reaches the entry point through
`src/components/ide/store/chat-submitter.ts` (`setChatSubmitter`,
`sendToChat`), which `chat-submission.ts` registers itself with when it loads,
as the store registers the host resolver. Removed: `pendingChatSubmitByChatId`,
`queueChatSubmit`, `takePendingChatSubmit`, the `PendingChatSubmit` type, the
runtime's drain (`drainPendingSubmit(s)`, `serializeQueuedSubmission`,
`isEmptySubmission`, `restoreDraft`, its `draining` set and store
subscription), `submitChatPrompt` and `queueFeedbackSubmit`. Callers: the
chat panel's composer awaits the answer and throws its message to keep the
composer's input; `executeStashItem` sends and removes the item (returning the
chat as before); `runSavedPrompt` returns the answer, or null when its own
checks fail; browser-element and inline-diff feedback send after
`resolveFeedbackChatId` picks the chat. A new `messageStillSending` message
is in every locale.

Behaviour: where the copies of the gate disagreed, the stricter rule now holds
for every sender. A deleted chat is refused (only the queue checked it; the
composer never shows one). One message at a time is sent to a chat from this
window: the queue refused a second while one waited, but the composer chained
any number, so pressing Enter again while a message was still on its way sent
the same draft twice; now the second is refused as busy, silently (the banner
stays the first message's) and the composer keeps it. Host away, missing
provider CLI and no model are refused at once rather than after the queue
accepted the message. Because the busy mark now lasts until the host has the
message, and covers the composer's sends, Chat activity says a chat does not
accept a message for that whole time (before, only while a queued message
waited for its transcript); the stash, saved-prompt and feedback controls
follow it. A stash item sent to a new chat that does not take it now goes to
that chat's draft (it was lost); a stash item the chosen chat refuses as busy
is removed and goes to the draft with no toast (the panel already disables
that chat). Feedback no longer shows "This chat already has a message in
progress" in its popover; its chat picker's busy check is unchanged.

Validation: `pnpm check` passed (scratch check, `biome check .`,
`tsc --noEmit`, vitest: 227 files, 1634 passed, 4 skipped).
`chat-submission.test.ts` (9 tests) drives `sendChatMessage` over the real
runtime and store with the host routes stubbed: a stash message sent and saved
with no panel mounted, clearing the busy mark and activating the chat; a
composer message sent with its skills shown and its draft emptied; each
refusal reason (not in the active project, deleted, busy, host away, provider
CLI missing, no model) as a value with its banner, no request, and the text in
the draft; an empty message refused with no banner; a refused composer message
leaving the draft as it was; a second message refused as busy while the first
is sent, and a chat streaming here taking the next; a failed send answering
its error and returning feedback text to the draft while a composer draft is
left as it was; the lost-receipt retry; and a saved prompt run through the
store reaching the same entry point. The runtime's submission tests moved
there; stash and saved-prompt action tests register a fake submitter and
check what the store sends; the activity and store fixtures use
`sendingChatIds`.

Remaining/deferred: "accepts a message" and the gate still differ on purpose
about a chat streaming here: the gate takes the message (the host queues it,
as the composer relies on), while the stash, saved-prompt and feedback
controls offer only chats that accept one. The unused `alreadyStreaming`
message is left in the locales. The app was not run.

## ARC17-03: A branch's base

Status: implemented

Problem: which ref a branch's base is gets answered five ways in the host's
git modules. `getPullRequestBaseRef` prefers the remote branch;
`resolveWorktreeBaseBranch` prefers the local one; the push preview has its
own chain; `readBranchMergeState` checks both; pull request generation and the
client's branch actions fall back to `"main"` though `defaultBranch` already
tried main and master. Under them sit several one-line ref reads, each with
its own failure value. None of the base resolution is tested.

Scope: Repository context answers a branch's base (`baseOf`): the base branch,
the ref to compare with, the remote, and whether it exists, under one
remote-or-local rule and one outcome when none is found. The one-line ref
reads move behind it. Callers keep their own wording. The client's fallback
follows the host's answer.

Completion criteria:

- Push preview, worktree compare and merge, branch deletion's merge check and
  pull request generation read the base through the one function.
- One documented preference between the local and remote base branch, and one
  "none found" outcome; any deliberate difference between callers is a named
  option.
- No `"main"` literal fallback remains where the host already answered.
- Temp-repository tests cover: local only, remote only, both diverged, none.

Implementation: `baseOf(repoRoot, { base? })` on the Repository context
(`electron/api/project-git/repository-context.js`, `gitRepositories` in
core.js). `base` is a branch the caller was given (a worktree's recorded base,
a pull request's requested base, `refs/heads/` stripped); without one it is the
default branch. The answer is `{ baseBranch, remoteName, localRef, remoteRef,
compareRef, mergeRef }`, with `localRef`/`remoteRef` the full refs that exist
(null when one does not), or `null`, the one "none found": no base named, or
neither ref exists. The preference: `compareRef` is the remote branch when it
exists, else the local one, since what work adds to its base is what it adds
to the base everyone else sees. The deliberate difference is a separate field,
`mergeRef`, the other way round: finishing a worktree merges into the local
base branch (checking it out in the main checkout, which creates it from the
remote branch when there is none), so what it would add is read from there.
The answer is a stable fact (remembered like the default branch, forgotten on
any write, a null not kept): which refs exist, never where they point. Beside
it, `ref(cwd, ref)` (the commit a ref names, or null) and `count(cwd,
revisions)` (`rev-list --count`, null when git cannot say) replace the one-line
reads. Callers: the push preview compares a branch with no upstream and no
remote branch of its name with `compareRef`; pull request generation reads its
commits and diff stat from `compareRef`, proposing a requested base the
repository has not fetched by name with no commits read (as before), and
throws "Unable to determine the base branch for this pull request." when none
is named or found instead of using `"main"`; the worktree's
`resolveWorktreeBaseBranch` (compare, compare diff, merge) compares with
`mergeRef` and reports `baseExistsLocally` from `localRef`, keeping its two
messages; branch deletion takes the base's name for the "is the base branch"
refusal and both existing refs for the merge check. Removed:
`getPullRequestBaseRef`, `readGitCommitCount` (actions.js), `gitRefExists`
(core.js), `readGitRef`/`readGitHead` (actions.js), `hasGitRef`
(worktree-lifecycle.js), and the bodies of `countCommits`/`readBranchHead`
(branches.js, now one line over `count`/`ref`); `defaultBranch` checks main
and master with the same `ref`. Client: `getBranchActions` has
`createPullRequest: null` when the full status reports no base branch, and
the footer then lists no create action and opens no dialog.

Behaviour: a branch whose repository has no base branch the host can find
(no remote HEAD, no main or master, locally or on the remote) is no longer
offered "Create pull request" into a `main` it does not have; the host refuses
such a request rather than generating details against `main`. The push
preview's `baseRef` and the worktree compare's `compareRef` are now full refs
(`refs/remotes/origin/main`, `refs/heads/main`); no client reads them. A
push preview or compare whose commit count fails reports 0 as before.
Which base refs exist is now remembered for up to 30 seconds, so a base
branch created or deleted from a shell is seen within that, or at once after
any write the host makes.

Validation: `pnpm check` passed (scratch check, `biome check .`,
`tsc --noEmit`, vitest: 228 files, 1641 passed, 4 skipped).
`branch-base.test.js` (6 tests) drives real temporary repositories through
`baseOf` and its callers: a base only local (compare and merge ref both the
local branch); a base only on the remote (both the remote branch, and a
worktree compare against it with `baseExistsLocally` false); a diverged base,
where the push preview and pull request details count the local base's
unpushed commit against `origin/main` while a worktree compare against the
local branch is one ahead and none behind (the deliberate difference); branch
deletion counting a branch merged into either ref as merged; a requested base
with `refs/heads/` and a missing one; and none found, where pull request
generation, the delete preview and the worktree compare (default and requested
base) each answer in their own words. `branch-actions.test.ts` replaces the
"`main` when unknown" case with no create action when the host reports no
base. `repository-context.test.js` and `status.test.js` follow the default
branch's ref lookup moving from `show-ref` to `rev-parse`.

Remaining/deferred: the status's `baseBranch` (and the branch list's "base"
block) is still the default branch's name from `defaultBranch`, not `baseOf`;
`defaultBranch` only names a branch it found, except a remote HEAD pointing at
a branch that is gone. Reads of the current branch (`branch --show-current`
in worktree-lifecycle.js, `symbolic-ref` in the pull, `getGitRepositoryInfo`)
and `getGitDiffBaseRef` were left where they are. GitHub's own default branch
is not asked, so a repository whose base only GitHub knows still offers no
pull request. The app was not run.

## ARC17-04: Route adapters

Status: implemented

Problem: the SSH route sits under two connection supervisors. The SSH
connection has its own reconnect loop, port-forward restore, stable local
ports and pinned identity; its only production caller,
`desktop-connections.js`, passes `autoReconnect: false` and a fresh key each
attempt, so that machinery never runs, and its tests exercise only that path.
Each route adapter (SSH, written inline in `desktop-connections.js`, and
`https-route.js`) runs Host verification's steps in its own order, and they
already disagree (a catalog 401 is fatal over SSH, not over HTTPS). The route
supervisor and both adapters have no tests.

Scope: a route adapter opens one link and reports it lost. The route
supervisor owns retry, the readiness sequence (authorize, catalog probe,
protocol check, catalog matches host), fatal classification, pinning and
stable port relays. The SSH adapter moves out of `desktop-connections.js`.
The SSH connection's own reconnect, forward restore and pinned identity are
removed where nothing uses them. Host verification's predicates are not
changed.

Completion criteria:

- One readiness sequence and one fatal classification, used by both adapters.
- No reconnect loop or port-forward restore below the supervisor.
- The pinned identity is held once per connection.
- The supervisor is tested over a fake adapter: success, a lost link and
  retry, a fatal refusal, and a host that is not the pinned one.
- Existing SSH and desktop host checks pass.

Implementation: the adapter contract is written as JSDoc typedefs in
`electron/shared/route-supervisor.js`: a `RouteAdapter` is `open(route,
{signal, background, expectedIdentity, onLost})`, resolving with one
`RouteLink` `{ endpoint, request, authorize?, forwardPort?, close }` or
rejecting with why (`fatal` where retrying cannot help, `cancelled` where the
user declined). `request` is a fetch carrying the link's credential;
`authorize` is the transport's own authorization step, answering with the
host's response; `endpoint` is read after it. `onLost` may be called at any
time after `open`: before the link is selected it fails that attempt with the
reason, after it the supervisor drops the link and dials again. An adapter
never reconnects. The supervisor owns the rest. `readyLink` is the one
readiness sequence: authorize; the pinned host (and, beside other routes, a
persistent identity), before any catalog request; the catalog probe; the
protocol check (the catalog's version, else the endpoint's); the catalog
naming the endpoint's host. `routeRefusal` is the one rule for a refusal:
a 401 or 403 from authorization, the catalog probe or an HTTPS link's later
session renewal is fatal (the route is blocked until an explicit connect);
any other status cools down and retries. A wrong host, an unsupported
protocol and a catalog for another host are fatal as before. The supervisor
adds `routeId` to the endpoint and holds the pinned identity
(`getPinnedIdentity`); `getHandle` became `getLink`.

The SSH adapter moved out of `desktop-connections.js` into
`electron/connections/ssh-route.js` (`createSshRoutes`), beside
`https-route.js`: one SSH connection per link under its own key, prompts
asked under the connection's host id, a session that ends after opening
reported through `onLost`, and the daemon's token on every request. The
HTTPS adapter's `open` now stops at the transport: the credential and grant
checks before any credential is sent are unchanged, its session renewal is
`authorize`, and the 15 s renewal poll starts once authorized and reports a
refusal with `routeRefusal`. `desktop-connections.js` keeps one supervisor
per host, picks the adapter by route kind, and keeps the stable local port
relays; its copy of the pinned identity is gone (the "pinned to a different
host identity" check reads the supervisor's).

Removed from the SSH layer: `ssh-host-connection.js`'s reconnect loop
(`RETRY_DELAYS_MS`, `STABLE_AFTER_MS`, `scheduleRetry`, `autoReconnect`,
the `random` and `clearTimer` options), its port-forward restore and
reuse of a forward's local port across links, and its pinned identity
(`expectedIdentity`, `identityProblem`). A dropped session now ends the link
as `disconnected` with "The SSH connection closed." `ssh-hosts.js` lost
`autoReconnect`, `expectedIdentity` and the "already connected" early return
with its identity check; `connect` replaces any connection under the same
key. Callers checked: `desktop-connections.js` (the only production caller,
always `autoReconnect: false` with a fresh key per attempt),
`scripts/ssh-host-check.mjs` (one connect, then `disconnectAll`; it never
relied on reconnecting), `host-install.test.js` and the SSH tests;
`main.js`, `desktop-handlers.js` and `desktop-launch.js` reach SSH only
through the desktop connections. The ensure step's protocol check and the
host-info probe that confirms the forward reaches the daemon stay in the SSH
connection, as transport steps. Host verification's predicates are
unchanged; `remote-access.js`'s own `httpsOrigin` was left alone.

Behaviour: a catalog 401 or 403 over HTTPS now blocks the route, as it did
over SSH; it used to cool down and retry. Over HTTPS a 401 or 403 while
authorizing now fails with the device-grant message ("This device's grant
was revoked, expired, or lacks access. Pair again on the host.") instead of
"The HTTPS route refused access (401).", still fatal. Refusal wording is now
one per step for both routes ("The route refused access (n).", "The route
refused catalog access (n).", "The route's catalog does not match its
verified host."). An SSH route that reaches another host, or a host that
does not name itself once one is pinned, is refused with the supervisor's
"This route reaches a different host than the saved connection." instead of
the SSH connection's two messages naming the target. A lost SSH link reports
"The SSH connection closed." No client matches on any of these strings.

Validation: `pnpm check` passed (scratch check, `biome check .`,
`tsc --noEmit`, vitest: 231 files, 1662 passed, 4 skipped).
`route-supervisor.test.js` (14 tests) drives the supervisor over a fake
adapter with a hand-moved clock: a ready link selected with its route id and
its host pinned; a lost link cooling down and dialed again, expecting the
pinned host; a 503 retried; 401 and 403 from the catalog probe and from
authorization blocking the route with no retry scheduled until an explicit
connect; a refused authorization skipping the catalog probe; an unsupported
protocol and a catalog for another host refused; a host that is not the
expected one refused before its catalog is read; a route that reaches
another host after a loss blocked with the pin kept; a link lost before it
is ready failing the attempt with its reason; a host without a persistent
identity refused beside other routes; and a lost preferred route falling
back. `ssh-route.test.js` (5) covers the SSH adapter over a fake SSH host
manager, and `desktop-connections.test.js` (2) a connection over it: the
catalog probe with the daemon's token, the pin refusing a different saved
host, and a catalog 401 blocking the route. In `ssh-host-connection.test.js`
the reconnect test became "a dropped link ends it without dialing again,
and the daemon keeps running" (a new connect reaches the same daemon), the
multiplexed master drop now ends the link with no further ssh calls, and the
forward-restore test became one forward per port while the link lasts,
shared by concurrent callers and ended with the link. No real SSH host or
paired HTTPS host was reachable here, and the app was not run.

Remaining/deferred: a live walkthrough should check, over a real SSH host,
that a first connect prompts and a background probe does not; that killing
the SSH session (or the host's network) shows the route reconnecting and
then connected again, and a browser panel page through a forwarded port
comes back at the same local address; that a host replaced behind the same
target is blocked with the different-host message; and, over a paired HTTPS
route, that revoking the device on the host blocks the route (including
when the catalog request is the one refused) while a host restart only
cools it down. The HTTPS adapter has no test of its own (its TLS proof needs
a real TLS host); the connect payload and the status reason are ARC17-05's.

## ARC17-05: Routes to dial

Status: implemented

Problem: connecting a saved host translates its routes at three hops. The
renderer's `connectHost` joins saved routes with `settings.sshHosts` and picks
one of three payload shapes; the desktop handler validates `routes` and an
`sshRoutes` shape nothing sends; desktop connections fills in a default SSH
route. The same join is written again in the connections settings, the host
choices and the open-project dialog. On the way back, the supervisor's fatal
identity refusal is flattened by `main.js` and reaches the renderer as
"offline"; the renderer recovers "incompatible" by catching
`HostIdentityError` after a catalog load.

Scope: a shared module resolves a Saved host connection and the SSH settings
into the routes to dial, imported by the renderer and main. The desktop bridge
carries that one shape and validates it once. The connection status carries
its refusal reason so the renderer maps `incompatible` and `unauthorized` in
one place.

Completion criteria:

- One route shape crosses the desktop bridge; `sshRoutes` and the bare
  `target` payload are gone.
- Every saved-route to SSH-settings join calls the shared module.
- A fatal identity refusal reaches the renderer as `incompatible` from the
  status, without relying on a catalog load.
- Table tests for route resolution; a handler test for the one shape.

Implementation: `electron/shared/routes-to-dial.js` is the shared module,
imported by the renderer and the main process. `routesToDial({ connectionId,
saved, sshHosts })` answers the one shape that crosses the desktop bridge,
`HostConnectRequest` `{ hostId, routes, expectedIdentity }` (types in
`src/types/ide.ts`, `DialRoute` for each route): a saved connection's routes

## ARC17-07: Reaching a Host

Status: implemented

Problem: one host's connection lifecycle is tracked in seven places
(`IdeState.hosts`, the connection supervisor, `connecting`/`stopped` in
host actions, `suspended`/`pending` in the catalog lifecycle, `removing` in
saved connection edits, connection recovery, and a watcher map in an
`IdeShell` effect), and "is the host there" has three rules: connected and
loaded (`isHostAway`, `openProject`, `reachHost`), connected
(`connection-follow`), loaded (the `IdeShell` watchers). The home host is
absent from `hosts`, so its readiness is read from the supervisor. Which
hosts get catalog and browser watchers, re-watching on a route change and
the browser-lending rule live in a React effect no test reaches.

Scope: one Host reach owner outside React, like the Terminal session owner:
`reach(hostId)` (connect when needed and wait for its catalog), `isReady`
(one rule, the home host included), and the watchers (catalog events, browser
lending) started and stopped from host state, not from an effect. Callers of
the three readiness rules ask it. Saved host connection edits, the route
supervisor and catalog readiness keep their own responsibilities.

Completion criteria:

- One readiness answer used by `isHostAway`, opening a project, standalone
  chats and connection following; the home host answered the same way.
- The watcher and browser-lending rules are outside React and tested: which
  hosts are watched, re-watching on a route change, lending only where the
  rule says.
- `IdeShell` only starts and stops the owner.

Implementation: `src/components/ide/store/host-reach.ts` is the Host reach
owner. `createHostReach(get, parts)` is built once in `ide-store.ts` as
`hostReach`, beside the Terminal session owner, and handed to

are injected: `connect` (the store's `connectHost`), `home` (the home
host's connection, from the connection supervisor), `watchCatalog`,
`watchBrowser` and `desktop`. Its interface: `isReady(state, hostId)`,
`reach(hostId)` and `follow(store)`. The rules are pure functions beside it.
`isHostReady(state, hostId, home)` is the one readiness rule: ready means
connected with its catalog in this window. An SSH or paired host is ready
when main reports it `connected` and its catalog is `loaded`. The home host
is not in `hosts`: it is ready when the supervisor says `ready` and the
workspace is hydrated (`stateHydrated`), since hydration is where its
catalog comes in. A second rule, `isHostConnected`, is the transport alone
(the supervisor's `ready` for the home host): what listing folders in the
open-project dialog needs. `recoverableHostIds` is what connection
following gives connection recovery, kept distinct on purpose: none before
hydration, then the home host (the connection runtime recovers its
connection itself) and every host whose transport is connected, catalog
loaded or not, because bringing the catalog in is recovery's job.
`reach` resolves true at once for the home host (nothing here connects it)
and for a ready host; otherwise it calls `connect`, which resolves once the
catalog is loaded. `follow(store)` is the former `IdeShell` effect:
`watchedHostIds` (the home host always, any other once loaded) each get a
catalog watcher, started again when the host's `routeId` changes;
`lendsBrowser` decides lending (no desktop, none; a route of kind `https`,
none; the home host only when the desktop's `hostMode` is `detached`);
hosts that leave the watched set are stopped; and main's `onHostStatus`
reports go to `setHostStatus`. It returns the stop. `IdeShell` is now
`useEffect(() => hostReach.follow(useIdeStore), [])`.
`watchHostCatalog` and `watchHostBrowser` take the followed store as an
argument instead of importing `useIdeStore`, so the owner can import them
without an import cycle through the store.

Callers: `isHostAway` (`ssh/host-away.ts`, now over `awayHost`) asks
`isHostReady` for every project, the home host included, and describes the
home host from the supervisor (`HOME_HOST_STATE`, moved from
`project-host-label.tsx`); chat submission's gate and `useHostAway` (the
host-away notice and the right panel) use it. `openProject` and
standalone chats (`createStandaloneChat`, `showStandaloneChat`) call
`reach`, and so does the open-project dialog's typed-path attempt instead
of `connectHost`. `followConnections` gives recovery `recoverableHostIds`.
The open-project dialog's `reachable` is `isHostConnected`; chat search
asks `hostReach.isReady` for the hosts besides the home host, which it
always asks so a failure there shows.

Behaviour: the home host is now answered by the same rule. In a browser
client whose home host's connection is not ready (connecting,
reconnecting, offline or refused), a home project's chat refuses to send
with the host-away message instead of sending a request that fails; the
host-away notice shows above the composer, without a Reconnect button
(the connection runtime brings the home host back itself, on foreground
and online), and the right panel's file tree loads again when it comes
back. On the desktop the home host is ready from startup, so this shows
only when its catalog was refused as another host (`incompatible`). In the
open-project dialog, typing a path on a host that is already ready no
longer dials it again and reloads its catalog before listing the folder.
Everything else is as it was: which hosts are watched, re-watching on a
route change, lending, recovery's hosts, opening a project and standalone
chats on a host that is or is not ready.
