# November 14 architecture review

The user selected all eight candidates from the visual review, in order, with a
commit after each. The review identified them from source inspection; the
scenarios it describes were not reproduced unless a section says so.

## ARC14-01: Host verification

Status: implemented

Problem: whether the host a route reached is the host a connection expects is
written seven times (route supervisor, both SSH modules, both route adapters,
saved host connections), and the copies disagree on a host that reports no
fingerprint. "Ask a host who it is" and "the catalog's host matches the
endpoint just verified" are each written per caller. No test references the
route supervisor or either route adapter.

Scope: one Host verification module owns the pinned-identity predicate, the
protocol check, the host-info probe and the catalog-matches-endpoint check.
Callers keep their own timing (early refusals before a credential is sent stay
early) and their own refusal wording. Host identity, saved host connections and
the route supervisor keep their responsibilities.

Completion criteria:

- Every pinned-identity comparison calls the one predicate; any deliberate
  difference between callers is an explicit, named option.
- Existing SSH, desktop host and codec checks pass.
- The predicate has a table test, including a host with no fingerprint.

Implementation: `electron/shared/host-verification.js` owns the
pinned-identity predicate (`matchesPinnedIdentity`), the protocol check
(`hostProtocolProblem`, moved from `host/protocol.js`, which keeps the
version constants), the host-info probe (`requestHostInfo`), the catalog
probe (`requestCatalogProbe`) and the catalog-matches-endpoint check
(`catalogMatchesHost`). It has no Node built-ins, since saved host
connections run in the renderer too, so callers pass their credential
header. All seven pinned-identity sites call the predicate: the route
supervisor, `ssh-host-connection.js`, `ssh-hosts.js`,
`desktop-connections.js`, both checks in `https-route.js` (the early one
still refuses before a device credential is sent) and `host-connections.js`.
Each keeps its own guard for "nothing pinned yet" and its own wording.
`desktop-host.js` layers its pid and public key checks on the predicate; its
local identity always has a fingerprint, so the comparison is still exact.
Both route adapters send the catalog probe and compare its host through the
module. The daemon, desktop host and SSH connection ask for host-info
through it, with the same 2 s timeout and their own handling of a refusal.

The SSH host-info probe now refuses redirects, as the other two did. A
Dream host does not redirect `/api/host-info`; a redirect now reads as no
answer instead of being followed with the token.

`daemon.js` still compares the protocol version itself. It asks whether a
running daemon speaks this runtime's own protocol, which `ensure` reuses
only then; `hostProtocolProblem` asks whether a client can talk to a range
of versions. The two agree today only because the range is 1 to 1.

Missing fingerprint: saved host connections accepted a host that names the
saved host ID but no fingerprint; every other site refused it. That
leniency is now gone. Evidence it was not deliberate: it arrived in
370a6902, the commit that added host identity, with no comment or test.
In that same commit `getHostDescriptor` started listing `hostId` and
`fingerprint` together, from `host-identity.json`, whose fingerprint is
recomputed from the key, so no host has ever listed an ID without a
fingerprint. `HostDescriptor.fingerprint` is typed as required. A saved
record with no fingerprint still accepts any fingerprint and records it. The
local route is still never refused.

Validation: `pnpm typecheck` passed. `pnpm vitest run` on the new test,
`electron/shared`, `electron/ssh`, `electron/desktop-host.test.js`,
`electron/host/daemon.test.js`, `electron/desktop-handlers.test.js` and
`electron/api/host-proxy-routes.test.js`: 14 files, 173 checks passed and 1
skipped. `pnpm vitest run electron src/lib`: 130 files, 938 passed and 4
skipped; one earlier run had a timing failure in `run-scheduler.test.js`,
which imports none of the changed modules, and it passed on two reruns.
`pnpm biome check` on the changed files passed. Added
`electron/shared/host-verification.test.js` (17 checks): the predicate
table, including a host with no fingerprint, the catalog match, the
protocol check, and a saved connection refusing a host that drops its
fingerprint.

Remaining/deferred: the route supervisor and both route adapters still have
no tests of their own. No live SSH, HTTPS or detached home host connection
was exercised.

## ARC14-02: A Project on its Host

Status: proposed

Problem: requests carry a path plus an optional Host, and "no Host given" is
decided three ways: guess by path (active Project first), assume local, or read
the Project. Callers that know the Project still send only its path (File
editor session reads and writes, directory lists, image preview, text search,
Skill catalog key).

Scope: every caller that knows the Project names its Host, through one way of
deriving it from a Project. The path-only guess remains only for callers that
have nothing but a path.

Completion criteria:

- Project requests, resource keys and caches built from a known Project carry
  its Host.
- The File editor session reads and writes on its Project's Host.
- Relevant tests, typecheck and lint pass.

## ARC14-03: Branch actions

Status: proposed

Problem: `git-actions/next-step.ts` is tested and has no production importer;
the live rule for which git actions a branch offers is inline and untested in
`git-panel/footer-actions.tsx`, and the two disagree on offering a pull
request when it is unknown or merged.

Scope: one pure module answers which Project git writes a branch offers; the
footer menu and the dialogs read it. The unused copy becomes that module or is
removed.

Completion criteria:

- The footer menu and dialogs read one rule.
- Its tests cover the cases on which the two copies disagreed.

## ARC14-04: Agent CLI run

Status: proposed

Problem: one-shot prompt runners each spawn, read output, map errors and time
out for themselves. Chat titles pass a timeout to every Provider, but the
Claude, Codex and Cursor runners ignore it, and no runner can be stopped.
Antigravity's argument and stdin rules are written for the turn and again for
the one-shot.

Scope: one module runs an agent CLI process to completion: spawn, output lines,
a bounded stderr tail, spawn-error mapping, exit-code errors, timeout and stop.
Runners supply arguments and translation. Long-lived JSON-RPC processes (ACP
connection, Codex app server) are excluded.

Completion criteria:

- Every one-shot runner honours its timeout.
- Antigravity's launch rules exist once.
- Existing provider tests pass.

## ARC14-05: Terminal session

Status: proposed

Problem: one Terminal session is spread over three module singletons, seven
store maps and the terminal client, and each lifecycle path updates them by
hand. Restore, output acknowledgement and discovery are decided in an
`IdeShell` effect.

Scope: a session's state and what host events do to it move behind one
Terminal session owner outside React. The store keeps what panels render; the
xterm view stays in the terminal panel.

Completion criteria:

- Opening, closing, closing a Project and removing a Host go through the owner.
- Restore, acknowledgement and discovery are outside React.
- Existing terminal tests pass.

## ARC14-06: Desktop launch

Status: proposed

Problem: the desktop launch and quit sequence runs as top-level statements in
`electron/main.js`, so only a booted Electron exercises it.

Scope: the launch and quit sequence moves into a module that takes Electron's
parts as arguments. `main.js` keeps windows, shortcuts and navigation guards.
Desktop startup (`renderer-server.js`) is unchanged.

Completion criteria:

- Launch and quit order unchanged; host options assembled once.
- Existing desktop host, host mode and renderer server checks pass.

## ARC14-07: Turn prompt

Status: proposed

Problem: five Provider adapters each decide what a turn sends given whether it
resumed, and the copies drifted: only Codex bounds the reconstructed prompt.

Scope: one module builds the prompt from how the turn started, the handoff,
references and attachments. Adapters keep their native probe and their report
of how the turn started. Reopens the prompt-construction part of PSD-01.

Completion criteria:

- Every adapter builds its prompt through the one module.
- Existing replay tests pass.

## ARC14-08: Provider presentation

Status: proposed

Problem: adding a Provider is one row and one record on the host, but the
renderer also needs a hand-copied settings card, three memos and handlers per
Provider, and several label tables, one of which mislabels Grok and
Antigravity.

Scope: a Provider's labels and icon are read from one table keyed by
`AiProvider`; the settings card renders once per Provider.

Completion criteria:

- One label table; the skills section labels every Provider correctly.
- The settings page renders Provider cards from the table.
- Typecheck and lint pass.
