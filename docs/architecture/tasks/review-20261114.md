## ARC14-01: Host verification

Status: implemented

Problem: whether the host a route reached is the host a connection expects is
written seven times (route supervisor, both SSH modules, both route adapters,
saved host connections), and the copies disagree on a host that reports no
fingerprint. "Ask a host who it is" and "the catalog's host matches the
endpoint just verified" are each written per caller. No test references the
route supervisor or either route adapter.

Scope: one Host verification module owns the pinned-identity predicate, the
protocol check, the host-info probe and the catalog-matches-endpoint check.
Callers keep their own timing (early refusals before a credential is sent stay
early) and their own refusal wording. Host identity, saved host connections and
the route supervisor keep their responsibilities.

Completion criteria:

- Every pinned-identity comparison calls the one predicate; any deliberate
  difference between callers is an explicit, named option.
- Existing SSH, desktop host and codec checks pass.
- The predicate has a table test, including a host with no fingerprint.

Implementation: `electron/shared/host-verification.js` owns the
pinned-identity predicate (`matchesPinnedIdentity`), the protocol check
(`hostProtocolProblem`, moved from `host/protocol.js`, which keeps the
version constants), the host-info probe (`requestHostInfo`), the catalog
probe (`requestCatalogProbe`) and the catalog-matches-endpoint check
(`catalogMatchesHost`). It has no Node built-ins, since saved host
connections run in the renderer too, so callers pass their credential
header. All seven pinned-identity sites call the predicate: the route
supervisor, `ssh-host-connection.js`, `ssh-hosts.js`,
`desktop-connections.js`, both checks in `https-route.js` (the early one
still refuses before a device credential is sent) and `host-connections.js`.
Each keeps its own guard for "nothing pinned yet" and its own wording.
`desktop-host.js` layers its pid and public key checks on the predicate; its
local identity always has a fingerprint, so the comparison is still exact.
Both route adapters send the catalog probe and compare its host through the
module. The daemon, desktop host and SSH connection ask for host-info
through it, with the same 2 s timeout and their own handling of a refusal.

The SSH host-info probe now refuses redirects, as the other two did. A
Dream host does not redirect `/api/host-info`; a redirect now reads as no
answer instead of being followed with the token.

`daemon.js` still compares the protocol version itself. It asks whether a
running daemon speaks this runtime's own protocol, which `ensure` reuses
only then; `hostProtocolProblem` asks whether a client can talk to a range
of versions. The two agree today only because the range is 1 to 1.

Missing fingerprint: saved host connections accepted a host that names the
saved host ID but no fingerprint; every other site refused it. That
leniency is now gone. Evidence it was not deliberate: it arrived in
370a6902, the commit that added host identity, with no comment or test.
In that same commit `getHostDescriptor` started listing `hostId` and
`fingerprint` together, from `host-identity.json`, whose fingerprint is
recomputed from the key, so no host has ever listed an ID without a
fingerprint. `HostDescriptor.fingerprint` is typed as required. A saved
record with no fingerprint still accepts any fingerprint and records it. The
local route is still never refused.

Validation: `pnpm typecheck` passed. `pnpm vitest run` on the new test,
`electron/shared`, `electron/ssh`, `electron/desktop-host.test.js`,
`electron/host/daemon.test.js`, `electron/desktop-handlers.test.js` and
`electron/api/host-proxy-routes.test.js`: 14 files, 173 checks passed and 1
skipped. `pnpm vitest run electron src/lib`: 130 files, 938 passed and 4
skipped; one earlier run had a timing failure in `run-scheduler.test.js`,
which imports none of the changed modules, and it passed on two reruns.
`pnpm biome check` on the changed files passed. Added
`electron/shared/host-verification.test.js` (17 checks): the predicate
table, including a host with no fingerprint, the catalog match, the
protocol check, and a saved connection refusing a host that drops its
fingerprint.

Remaining/deferred: the route supervisor and both route adapters still have
no tests of their own. No live SSH, HTTPS or detached home host connection
was exercised.

## ARC14-02: A Project on its Host

Status: implemented

Problem: requests carry a path plus an optional Host, and "no Host given" is
decided three ways: guess by path (active Project first), assume local, or read
the Project. Callers that know the Project still send only its path (File
editor session reads and writes, directory lists, image preview, text search,
Skill catalog key).

Scope: every caller that knows the Project names its Host, through one way of
deriving it from a Project. The path-only guess remains only for callers that
have nothing but a path.

Completion criteria:

- Project requests, resource keys and caches built from a known Project carry
  its Host.
- The File editor session reads and writes on its Project's Host.
- Relevant tests, typecheck and lint pass.

Implementation: `projectScope(project)` in `src/lib/project-resource-cache.ts`,
beside `ProjectScope`, is the one derivation: the Project's path and
`getProjectHostId(project)`, so a Project naming no Host is on the home Host.
Callers that know their Project now name that Host: the File editor session
(its dependencies give a scope instead of a path; reads and writes carry
`hostId`), the file explorer's directory reads, file list and image preview,
text search, the Changes row's deleted-image read
(`getProjectGitFileAtHeadRawUrl` takes a Host like `getProjectFileRawUrl`),
the footer's remote URL, the sidebar's worktree list, the composer's file
list, checkpoint cleanup (one request per Project instead of per path) and
the Skill catalog, keyed by provider, Host and path. The Skills settings page
sends its list, preview, toggle and create to the shown Project's Host, or the
home Host with no project.

`project.hostId` read raw is undefined for a home-host Project, so a key or
request built from it fell through to the path guess. None does now: the git
status, branches, pull-request context and branch-delete preview hooks, the
push and delete-branch dialogs and the project tab icon require a Host, and
their callers pass `getProjectHostId`. The commit draft, create pull request
dialog, git log, pull-request tab, worktree finish and commit warming already
fell back to the home Host; they use the same derivation. Project resources
match a scope to its Project and invalidate it by `projectScope` as well.
`resolveRequestHost` and the store's resolver note that the path guess is for
callers with only a path. No route changed; every Route client method
already accepted `hostId`.

One behavior change: a skill toggle was always sent to the home Host; it now
goes to the Host whose skills the page lists.

Validation: `pnpm typecheck` passed. `pnpm vitest run` on the tests beside
changed modules (chat runtime, File editor session, commit draft, worktree
finish, generated git text, Project resources), `src/lib` and
`src/components/ide/store`: 51 files, 377 passed. `pnpm vitest run src`: 105
files, 725 passed. `pnpm biome check` on the changed files passed. Added a
File editor session check that two sessions at one path read and write on
their own Hosts, and a Project resources check that a home-host Project and a
remote one at the same path each key, read and refresh on their own Host,
while the path alone guesses the active Project's.

Remaining/deferred: the write-file chip in chat transcripts reads git status
and diffs by path alone; its path is threaded through the message renderers
without the Project, so it keeps the guess, and `projectResourceKey` and the
raw file URLs still accept no Host for it. Opening in an editor or file
manager, the browser panel's loopback rule and Project identity calls
(`openProject`, `addProject`, worktree attach) take the raw `hostId`, where
absent already means the home Host. The background-Project refresh reading
from the wrong Host was not reproduced; a session now reads from its own
Project's Host whichever Project is active. No multi-host UI was exercised.

## ARC14-03: Branch actions

Status: implemented

Problem: `git-actions/next-step.ts` is tested and has no production importer;
the live rule for which git actions a branch offers is inline and untested in
`git-panel/footer-actions.tsx`, and the two disagree on offering a pull
request when it is unknown or merged.

Scope: one pure module answers which Project git writes a branch offers; the
footer menu and the dialogs read it. The unused copy becomes that module or is
removed.

Completion criteria:

- The footer menu and dialogs read one rule.
- Its tests cover the cases on which the two copies disagreed.

Implementation: `getBranchActions` in `git-actions/branch-actions.ts` takes
a full status read, the branch's pull request (a summary, none, `loading` or
`unavailable`), the worktree's base ref if the project is a worktree, and
whether a git write runs. It answers every action the branch offers at once,
each enabled or not: commit, push or publish (with the ahead count), fetch,
pull (with the behind count), view the pull request, create one (offered,
enabled, base branch, why the branch cannot propose one, the default and
allowed next steps), merge or remove the worktree (with the merge base), and
whether the trigger is highlighted. The footer menu reads it in place of its
inline checks. The push dialog takes the enabled push as a prop instead of
reading `hasPushableCommits` (removed from `utils.ts`) and the git write
itself. The create pull request dialog takes the create answer: its base
branch, the branch problem it words as an error, its default next step and
which next steps can be chosen. Its unused `baseBranch` override prop is
gone. `getPullRequestBranchError` is generic over its messages, so the
module asks it for codes. `next-step.ts` was the footer's single next-step
button (8ab08940); 53bd72c1 dropped the button for the menu and left the
module and its test unused. They are superseded and can be deleted.

Pull request still unknown: create is not offered while the lookup is
loading, so a branch with an open pull request is never offered a second.
`usePullRequestContext` gave null data both while loading and after a
failed lookup, and the lookup fails whenever `gh` is missing, signed out or
the remote is not on GitHub (`repository()` in `pull-requests.js` throws,
and the context route answers an error). Hiding create on "unknown" would
have removed it for those users for good. The hook now also returns
`lookupFailed` (the resource holds an error, also while retrying), and a
failed lookup still offers create, as before: `gh pr create` refuses a
duplicate and its error shows in the dialog.

Merged pull request: create is no longer offered. `branchPullRequest`
returns a closed or merged pull request only when `branchHasNoWorkBeyond`
finds the local branch tip is the PR head or behind it; once the branch has
a new commit the lookup answers none, and create is offered. So a merged
answer means there is nothing new to propose. A closed, unmerged one still
offers create.

Validation: `pnpm typecheck` passed. `pnpm vitest run
src/components/ide/git-actions src/components/ide/git-panel
src/components/ide/pull-requests`: 6 files, 58 passed. `pnpm vitest run
src`: 106 files, 737 passed. `pnpm biome check` on the changed files and
`git diff --check` passed. Added `branch-actions.test.ts` (12 checks): a
level branch, changes and commits ahead, publishing, the pull request
loading, unavailable, open, merged and closed, a worktree with no remote and
its merge base fallbacks, a detached HEAD, the base branch itself, the
create dialog's next steps, and a running git write.

Remaining/deferred: the create dialog now resets its form when its default
next step changes rather than when "has changes" or "needs push" changes;
the two differ only when a push becomes needed or not while files are
uncommitted, which no longer clears the form. With a merged pull request and
uncommitted files, create returns only once a commit is made and the
pull-request context is read again (at most every 15 seconds). The menu
was not inspected in the running app.

## ARC14-04: Agent CLI run

Status: implemented

Problem: one-shot prompt runners each spawn, read output, map errors and time
out for themselves. Chat titles pass a timeout to every Provider, but the
Claude, Codex and Cursor runners ignore it, and no runner can be stopped.
Antigravity's argument and stdin rules are written for the turn and again for
the one-shot.

Scope: one module runs an agent CLI process to completion: spawn, output lines,
a bounded stderr tail, spawn-error mapping, exit-code errors, timeout and stop.
Runners supply arguments and translation. Long-lived JSON-RPC processes (ACP
connection, Codex app server) are excluded.

Completion criteria:

- Every one-shot runner honours its timeout.
- Antigravity's launch rules exist once.
- Existing provider tests pass.

Implementation: `runAgentCli` in `providers/agent-cli-run.js` runs one CLI
process from a resolved launch (command, args prefix, Windows shell flag) to
completion. It writes stdin text or leaves stdin closed, reads stdout as JSON
lines for the caller's `onEvent` (a non-JSON line, or a detail the caller
reports, joins the error tail), keeps a 64,000-character stderr tail, words
spawn failures with the provider's message, rejects a non-zero exit with the
tail or `formatAgentCliExitMessage` ("`<X>` CLI exited with code N."), and on
`timeoutMs` or an aborted `signal` stops the process tree with
`stopChildProcess` and rejects ("`<X>` request timed out after Nms." or
"`<X>` request was stopped."). An error thrown by `onEvent` wins once the
process exits. The Codex, Cursor and Antigravity one-shots in
`generate-text.js` run on it and keep only their arguments and event
translation. Claude's one-shot goes through `ai-sdk-provider-claude-code`,
so it passes an abort signal (timeout or caller signal) to `generateText`,
which stops the Claude Code process; OpenCode's uses the same signal helper.
Grok's one-shot is an ACP connection: its `timeoutMs` already bounded the
prompt request, and `runGrokPrompt` now takes a `signal` that closes the
connection. Every one-shot defaults to two minutes, as OpenCode, Grok and
Antigravity already did; Claude, Codex and Cursor had no timeout, so a
commit message or pull request text from them now fails after two minutes.
Antigravity's prompt input (`-p`, or one stream-json user event on stdin for a
shell launch or a prompt over 30,000 characters) and its result-status error
are `getAntigravityPromptInput` and `getAntigravityResultError` in
`antigravity-cli.js`, used by the turn and the one-shot. The Antigravity turn
also runs its process on `runAgentCli`: a stop now rejects once the tree is
stopped, which `streamAgentTurn` drops for an aborted turn, as it resolved
before; a turn aborted before launch no longer spawns. `acp-connection.js`
uses the shared stderr limit and exit message.

Messages: OpenCode's timeout now reads "OpenCode request timed out after
120000ms." instead of "OpenCode request timed out.". Codex and Cursor one-shot
output is decoded as UTF-8 across chunks rather than per chunk. A non-zero
Antigravity turn exit now includes non-JSON stdout lines in its error, as the
one-shots did. The Antigravity one-shot keeps its messages.

Validation: `pnpm typecheck` passed. `pnpm vitest run electron/api/providers
electron/api/chat`: 38 files, 300 passed, including `generate-text.test.js`
(4) and `antigravity-stream.test.js` (15) unchanged. Added
`agent-cli-run.test.js` (10 checks) over a stand-in CLI
(`providers/test-fixtures/fake-agent-cli.js`, run with `process.execPath`):
stdin and JSON output, a failed exit with its stderr, a silent failed exit,
the stderr cap, a missing command, an `onEvent` error, timeout and abort each
stopping the fake and its grandchild, an already-aborted signal, and a hung
Cursor one-shot stopped by `timeoutMs`. `pnpm vitest run electron`: 112 files;
the only failures were load-dependent host tests (`host-proxy-routes.test.js`
on one run, `desktop-host.test.js` on another) that pass alone. `pnpm biome
check` on the changed files and `git diff --check` passed.

Remaining/deferred: the ACP connection and the Codex app server client keep
their own spawn and lifetime (Codex's stderr tail is still 20,000
characters); the other turn adapters were not moved. No caller passes a
`signal` to a one-shot yet (chat titles and git text would need a stop to
reach them). Grok's `timeoutMs` bounds only the prompt request; initialise,
authenticate and session creation keep the 30-second ACP default each.
Cursor still passes the prompt as an argument through `cmd.exe` on Windows,
as before. No real CLI was run.

## ARC14-05: Terminal session

store maps and the terminal client, and each lifecycle path updates them by
